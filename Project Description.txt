=========================================================
  PART 1 — PROJECT OVERVIEW (30-SECOND PITCH)
=========================================================

"I built ResumeLens, a full-stack AI-powered hiring platform that
automates the most time-consuming parts of recruiting. Recruiters
can post jobs, upload candidate resumes, and let the system
automatically score each candidate using a multi-step AI pipeline
built with LangChain and LangGraph. The results appear on the
recruiter's screen in real-time without any page refresh, using
Server-Sent Events. The system also generates personalized
rejection/interview emails using AI, detects duplicate candidates,
and provides candidates with a real-time status tracker link — all
without a recruiter having to do those tasks manually."

FRONTEND
  - Next.js 15 (App Router) — React framework for routing and SSR
  - React Query (@tanstack/react-query) — server state management,
    auto caching, auto refetching. NO Redux or Context needed.
  - Tailwind CSS + shadcn/ui — component library for the UI
  - Sonner — toast notifications

BACKEND
  - Node.js + Express.js — REST API server
  - MongoDB + Mongoose — primary database
  - Redis (Upstash Cloud) — message broker for BullMQ job queue
  - BullMQ — background job queue for AI processing
  - Server-Sent Events (SSE) — real-time push notifications to browser

AI / MACHINE LEARNING
  - LangChain — connects to OpenAI, builds prompts, parses outputs
  - LangGraph — orchestrates a multi-step AI pipeline as a graph
  - OpenAI GPT-4o-mini — the actual LLM model running all AI tasks

INFRASTRUCTURE / SERVICES
  - Cloudinary — stores uploaded PDF resumes in the cloud
  - Resend — transactional email provider (password resets)
  - Upstash Redis — cloud-hosted Redis for BullMQ
  - pdf-parse — parses raw text from PDF files

=========================================================
  PART 3 — ARCHITECTURE EXPLAINED SIMPLY
=========================================================

HOW A RESUME UPLOAD WORKS (End-to-End Flow):

  1. Recruiter fills form: Name, Email, PDF File, Job ID → clicks Upload
  2. Frontend sends a POST request to /api/resumes with FormData
  3. Backend (resumeController.js) runs multiple steps:
     a. Validates the job exists and recruiter owns it
     b. Parses the PDF text using pdf-parse (in memory, never on disk)
     c. Uses AI (LangChain) to extract Name, Email, Skills from the text
     d. CHECKS FOR DUPLICATES: queries MongoDB for same email
        - If same job → throws 409 error (blocked!)
        - If different job → saves isPastApplicant=true
     e. Uploads PDF buffer to Cloudinary, saves the secure URL
     f. Saves Resume document to MongoDB
  4. Frontend shows the new candidate card immediately

HOW THE AI SCREENING WORKS:

  1. Recruiter clicks "Screen" button on a candidate card
  2. Frontend calls POST /api/pipeline/screen
  3. Backend adds a "job" to the BullMQ queue in Redis. Returns 202 immediately.
     (This means: "I got your request, I'll do it in the background")
  4. The BullMQ Worker picks up the job from Redis and runs the LangGraph pipeline:
     - Node 1 (loadDocuments): Fetches Resume + Job from MongoDB
     - Node 2 (ensureEntities): AI extracts skills from resume if not done
     - Node 3 (ensureAnalyzedJD): AI analyzes the job description
     - Node 4 (scoreResume): AI scores the candidate 0-100 across 3 dimensions
     - Node 5 (saveResults): Saves Screening document to MongoDB
  5. When done, the Worker calls broadcastToUser() — this pushes a
     "screening_complete" event through SSE to the recruiter's browser
  6. The browser receives the event → React Query auto-refetches the candidate list
  7. The candidate card updates from "Screening..." to "Screened" with a score
  ALL OF THIS HAPPENS WITHOUT THE USER REFRESHING THE PAGE.

  PART 4 — COMMON INTERVIEW QUESTIONS & ANSWERS

GENERAL / ARCHITECTURE QUESTIONS
---------------------------------

Q: Why did you use Next.js instead of plain React?
A: Next.js gives us a lot of things out of the box:
   - File-based routing (no need for React Router)
   - App Router for easy layouts and nested routes
   - Server Components for better performance
   - Easy deployment to Vercel
   For this project, the (dashboard) route group lets me wrap all
   authenticated pages with a single shared layout/sidebar.

Q: Why MongoDB instead of a SQL database like PostgreSQL?
A: The data in this app is naturally document-shaped. A Screening
   result has nested objects (scoreBreakdown with technical,
   experience, culture sub-scores), arrays (matchedSkills,
   missingSkills), and mixed-type AI JSON blobs. MongoDB stores
   this naturally without needing complex joins. It also lets us
   add new fields (like isPastApplicant) without running migrations.

Q: Why did you use BullMQ and Redis for the AI screening?
A: The AI screening pipeline can take 10-30 seconds per resume
   because it calls OpenAI multiple times. If we ran this
   synchronously (blocking the HTTP request), the browser would
   time out and the recruiter would see an error. BullMQ lets us:
   1. Accept the request INSTANTLY (202 Accepted)
   2. Do the slow AI work in the background
   3. Notify the recruiter when it's done (via SSE)
   This way, the server can handle many recruiters screening
   candidates at the same time without slowing down.

Q: What is LangGraph and why did you use it?
A: LangGraph is a framework for building AI pipelines as a
   directed acyclic graph (DAG). Instead of writing one giant
   function that calls OpenAI, I built a pipeline with named
   "nodes" that each do one specific job.
   Benefits:
   - Each node is fault-isolated (if entity extraction fails,
     the pipeline can still continue or fail gracefully)
   - Nodes are idempotent (if entities were already extracted,
     the node skips the AI call — saves API costs!)
   - The graph is easy to visualize and debug
   My pipeline: loadDocuments → ensureEntities → ensureAnalyzedJD
                → scoreResume → saveResults

Q: What is Server-Sent Events (SSE) and why not WebSockets?
A: SSE is a one-way push channel from server to browser. The
   browser opens one persistent HTTP connection and the server
   pushes events over it whenever something happens.
   I chose SSE over WebSockets because:
   - Our use case is one-directional (server notifies client)
   - SSE is simpler to implement, uses standard HTTP
   - Works well through proxies and firewalls
   - No need for a separate WebSocket server
   In our app: when BullMQ finishes screening, it calls
   broadcastToUser(userId, 'screening_complete', data) which writes
   an SSE event to the recruiter's open connection.

Q: Explain React Query. Why not useState + useEffect for API calls?
A: useState + useEffect for data fetching leads to problems:
   - You have to manually manage loading, error, data states
   - No automatic caching (every component re-fetches the same data)
   - No automatic refetching when data changes
   - Race conditions with fast typing/clicking
   React Query solves ALL of these. Every query has a "queryKey"
   (a unique identifier). When I call queryClient.invalidateQueries(),
   React Query automatically refetches only the affected data. The
   app feels live without any manual polling.

SECURITY QUESTIONS
-------------------

Q: How do you protect your API endpoints?
A: Multiple layers:
   1. JWT Authentication — every protected route runs authMiddleware
      which verifies the JWT token from cookies or Authorization header
   2. Role-based authorization — some routes check req.user.role
      (e.g., only "admin" can deactivate users)
   3. Rate Limiting — global rate limiter: 100 requests per 15 minutes
      in production. Prevents brute force attacks
   4. Helmet — sets security HTTP headers (XSS protection, etc.)
   5. Custom XSS middleware — strips dangerous HTML from all inputs
   6. Custom NoSQL injection middleware — sanitizes MongoDB operators
      from request bodies
   7. Zod validation — all user inputs are schema-validated before
      touching the database

Q: How does the JWT system work?
A: When a user logs in, the server creates TWO tokens:
   - Access Token (short-lived: 7 days) — used to authenticate requests
   - Refresh Token — used to get a new access token without re-login
   The access token is stored in an HttpOnly cookie (cannot be read
   by JavaScript — protects against XSS attacks). The authMiddleware
   reads this cookie on every protected reque st, verifies it with
   JWT_SECRET, and attaches the user object to req.user.

Q: How is the public candidate tracker link secured?
A: Three ways:
   1. Unguessable ID — the URL uses the MongoDB ObjectId
      (24-character hex string). Attackers can't enumerate IDs.
   2. Data masking — the API ONLY returns: candidateName, jobTitle,
      company, friendlyStatus. It never returns the score, resume
      text, email, recruiter notes, or anything sensitive.
   3. Read-only — the endpoint only has GET, no POST/PATCH.
      Candidates can't change anything.

Q: How do you prevent duplicate candidates?
A: In the uploadResume controller, after extracting entities from
   the PDF, we check: "Does any existing resume have this email?"
   - If yes AND same job → throw 409 Conflict error (blocked)
   - If yes AND different job → allow upload but set isPastApplicant=true
   This check uses candidateEmail because emails are unique identifiers.
   Even if the candidate uses a different name, the email catches them.

PERFORMANCE QUESTIONS
----------------------

Q: How does your app handle multiple users simultaneously?
A: The key is the async queue architecture:
   - Express handles HTTP requests (very fast, non-blocking)
   - Slow AI work goes into BullMQ (Redis queue)
   - BullMQ Worker processes jobs one at a time (or we can scale to
     multiple workers)
   - The HTTP server is never blocked waiting for OpenAI to respond
   So 100 recruiters can all click "Screen" at the same time.
   Each request instantly returns 202. The queue processes them
   in order. Each recruiter gets notified via SSE when their
   candidate is done.

Q: What MongoDB indexes did you add and why?
A: I added indexes on the most common query patterns:
   - resumeSchema.index({ jobId: 1, status: 1 })
     → When you open a job page, we fetch all resumes for that job
       filtered by status. This index makes that query O(log n).
   - resumeSchema.index({ jobId: 1, createdAt: -1 })
     → When sorting resumes by upload date within a job
   - screeningSchema.index({ resumeId: 1 }, { unique: true })
     → Enforces one screening per resume at the database level
   - screeningSchema.index({ jobId: 1, overallScore: -1 })
     → When fetching all screenings for a job sorted by score
   Without indexes, MongoDB does a full collection scan (O(n))
   which is very slow at scale.

Q: What is the backoff strategy for failed AI jobs?
A: BullMQ is configured with:
   - attempts: 3 — try 3 times before giving up
   - backoff: exponential with 2000ms delay
     (waits 2s, then 4s, then 8s between retries)
   This handles transient OpenAI API errors (rate limits, timeouts)
   without immediately failing or hammering the API.

FRONTEND QUESTIONS
------------------

Q: Explain your folder structure in Next.js.
A: I use the App Router with route groups:
   - app/(dashboard)/ — all authenticated pages. Has a shared layout
     with sidebar. Includes: jobs, screening, pipeline, admin pages.
   - app/(auth)/ — login, register pages. Has its own minimal layout.
   - app/status/[resumeId]/ — the PUBLIC candidate tracker page.
     No auth, no sidebar. Just a clean tracking UI.
   This separation means auth pages and dashboard pages can have
   completely different layouts without any conditional rendering.

Q: How do you handle real-time updates on the frontend?
A: The useSSE hook in src/hooks/use-sse.js:
   1. Creates an EventSource connection to /api/events on mount
   2. Listens for specific event types (e.g., "screening_complete")
   3. When received, calls queryClient.invalidateQueries() for the
      relevant data (e.g., the resume list for that job)
   4. React Query automatically refetches the data
   5. The UI updates automatically — the recruiter sees the new score
      without pressing F5.

Q: What is prop drilling and does your app have it?
A: Prop drilling is when you pass data through many layers of
   components that don't use it, just to get it to a deeply nested
   child. Our app does NOT have this problem because:
   - Each page component fetches its own data using React Query hooks
   - Child components can call the same hook and get cached data
   - No "parent passes data to child to child to child" chains

Q: How do you handle loading and error states?
A: React Query provides isLoading and isError automatically for every
   query. I built shared components like <LoadingSpinner /> and
   error alerts that display based on these states. Every page has
   proper loading skeletons so the UI never shows empty/broken.

AI / LANGCHAIN QUESTIONS
-------------------------

Q: Explain how the AI scoring works.
A: The resumeScorerAgent.js uses LangChain with OpenAI GPT-4o-mini.
   It sends the parsed resume text, the analyzed job description,
   and the job's custom scoring weights (e.g., Technical 40%,
   Experience 40%, Culture 20%) to the AI.
   The AI returns a structured JSON with:
   - overallScore (0-100)
   - scoreBreakdown.technical, .experience, .culture (each with
     score + one-sentence rationale)
   - matchedSkills, missingSkills arrays
   - strengths, weaknesses paragraphs
   - recommendation (strong_yes, yes, maybe, no, strong_no)
   The output is parsed with Zod schema validation before saving
   to the database.

Q: What is the JD Generator feature?
A: When a recruiter types a Job Title and Company name, they can
   click a "magic wand" button. This calls the jdGeneratorAgent.js
   which uses LangChain + OpenAI to automatically generate a complete
   professional job description. It fills in the Description,
   Requirements, and Skills fields automatically, saving the recruiter
   20-30 minutes of writing.

Q: What is the Bias Detection feature?
A: The biasDetectorAgent.js analyzes job descriptions for biased
   language like "young and energetic" (age bias), "he/she" language
   (gender bias), or "native speaker" (nationality bias). It returns
   a list of flagged phrases with suggestions to replace them. This
   helps companies write more inclusive job postings.

DEPLOYMENT / PRODUCTION QUESTIONS
-----------------------------------

Q: What changes need to be made before production deployment?
A: Several things:
   1. Change MongoDB from localhost to MongoDB Atlas (cloud)
   2. Change NODE_ENV=production (activates stricter rate limiting)
   3. Set secure, unique JWT_SECRET values (don't use dev secrets)
   4. Verify a domain in Resend for sending emails
   5. Set CORS_ORIGIN to your actual production frontend domain
   6. Add a process manager like PM2 for Node.js
   7. Add database indexes for candidiateEmail field (for the
      duplicate detection query)
   8. Add environment variables to hosting platform (Vercel, Railway)
   9. Add proper logging (e.g., Winston) instead of console.log

Q: Is the app scalable?
A: Yes, the architecture is designed for horizontal scaling:
   - The HTTP server (Express) is stateless — can run multiple
     instances behind a load balancer
   - State is externalized: MongoDB for data, Redis for job queues,
     Upstash for Redis (already cloud-hosted)
   - SSE connections are the current bottleneck (each requires an
     open connection). For very large scale, you'd move to a
     Redis pub/sub model for SSE instead.
   - BullMQ workers can be scaled independently on separate servers
